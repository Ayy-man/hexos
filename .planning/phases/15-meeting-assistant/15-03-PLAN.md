<task type="auto">
  <name>Task 1: Create Recall.ai webhook handler</name>
  <files>app/api/webhooks/recall/route.ts</files>
  <action>
Create the webhook route following the EXACT pattern from `app/api/webhooks/stripe/route.ts`:

1. **Read raw body as text** (NOT json) — critical for Svix signature verification.
2. **Get Svix headers**: svix-id, svix-timestamp, svix-signature from request headers.
3. **Verify signature** using `new Webhook(process.env.RECALL_WEBHOOK_SECRET!)` from 'svix' package. Call `wh.verify(rawBody, svixHeaders)`. If verification fails, return 400.
4. **Parse the verified payload** to determine event type.

Handle these Recall.ai webhook events by looking up the meeting by recall_bot_id:

- **bot.joining_call**: Update meeting status to 'joining'
- **bot.in_waiting_room**: Update meeting status to 'joining' (no change, just log)
- **bot.in_call_recording**: Update meeting status to 'recording', set started_at to now()
- **bot.done**: This is the KEY event. Set status to 'processing', set ended_at to now(), calculate duration_seconds. Then call `processMeetingTranscript(meetingId, botId)` from `@/lib/api/meeting-processing`. Note: this processing happens inline (not async) — accept the risk for now per research recommendation. If it times out, Recall.ai will retry the webhook.
- **bot.fatal**: Set status to 'failed', store error_message from payload.

Use admin Supabase client (`@/lib/supabase/admin`) for database updates since webhooks have no user session.

For looking up meetings by bot ID: `supabase.from('meetings').select('id, created_by').eq('recall_bot_id', botId).single()`.

The event payload structure from Recall.ai:
```typescript
interface RecallWebhookEvent {
  event: string  // e.g. 'bot.done', 'bot.fatal'
  data: {
    bot_id: string
    status?: { code: string; sub_code?: string }
    // Additional fields vary by event
  }
}
```

Always return `NextResponse.json({ received: true })` for handled events. Return 200 even for unhandled event types (standard webhook practice).

Import `{ Webhook } from 'svix'`. This package needs to be installed — add a comment at top of file noting the dependency.

<task type="auto">
  <name>Task 2: Create AI transcript processing pipeline</name>
  <files>lib/api/meeting-processing.ts</files>
  <action>
Create the processing module that fetches transcripts and uses Claude for structured extraction.

**processMeetingTranscript(meetingId: string, botId: string)** — Main orchestrator:
1. Fetch bot details from Recall.ai: `recall.getBot(botId)` to get transcript download URL from `bot.media_shortcuts.transcript.download_url`
2. Fetch recording URL from `bot.media_shortcuts.video.download_url` (store as recall_recording_url)
3. Download transcript JSON from the transcript URL (separate fetch, NOT through recall client)
4. Transform transcript to our TranscriptSegment[] format (map speaker, text, start_time, end_time)
5. Store raw transcript in meeting record
6. Fetch linked project/inquiry names for AI context (query meeting_links + join project/inquiry names)
7. Call `extractMeetingData(transcript, linkedContext)`
8. Save AI results: update meeting with summary (join array to markdown bullets), key_decisions
9. Create meeting_tasks rows from extracted tasks (source: 'ai_extracted', created_by: meeting.created_by)
10. For each task's assigned_to name, attempt to match against profiles table by name (case-insensitive ILIKE on profiles.name). If match found, set assigned_to_profile.
11. Create meeting_participants from transcript speaker names. Attempt email/profile matching against profiles.
12. Update meeting status to 'ready'
13. Send push notification to meeting.created_by using `createNotification` from `@/lib/api/notifications`:
    - type: 'meeting_ready' (add to NotificationType union in notifications-utils.ts)
    - title: 'Meeting Notes Ready'
    - message: `Notes for "${meetingTitle}" are ready to review.`
14. If ANY step fails, set meeting status to 'failed' with error_message, and re-throw

**extractMeetingData(transcript: TranscriptSegment[], linkedContext: string)** — AI extraction:
1. Build prompt following the design doc's AI Processing Prompt section
2. Call OpenRouter API (existing pattern from `app/api/generate-brief/route.ts`):
   - URL: `https://openrouter.ai/api/v1/chat/completions`
   - Auth: `Bearer ${process.env.OPENROUTER_API_KEY}`
   - Model: `anthropic/claude-3-5-haiku-20241022` (fast, cheap for extraction)
   - Headers: HTTP-Referer, X-Title: 'hexOS Meeting Assistant'
   - System prompt: The meeting analysis prompt from design doc
   - User message: Formatted transcript text + linked project context
   - Request JSON response_format or parse the response as JSON
3. Parse Claude's response as MeetingAIExtraction type
4. Return the parsed extraction

Use `createClient` from `@/lib/supabase/admin` for all database operations.

Wrap the entire processMeetingTranscript in try/catch. On error:
- Update meeting status to 'failed' with error message
- console.error the full error for debugging
- Do NOT re-throw (webhook handler already returned 200)

IMPORTANT: The notification type 'meeting_ready' needs to be added to NotificationType in `lib/api/notifications-utils.ts`. Also add icon (Video) and color (blue) mappings in getNotificationIcon and getNotificationColor functions, and a URL mapping in getNotificationUrl that routes to `/meetings/${notification.project_id}` — but since meetings don't use project_id field for their own ID, we'll need to handle this. For V1, route to `/meetings` (the list page). The notification message itself contains the meeting title so the user can find it.
